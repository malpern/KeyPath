# KeyPath UI iteration on the Air

Use one active checkout and one installed candidate per iteration. The current checkout is `/Users/malpern/local-code/keypath-driverless-caps-ui` on mini/malpern; the interactive verification target is the Air.

1. Pick one concrete defect or small related group. Record the expected behavior and reproduce it before editing. For a bug, add a regression test that fails for the actual defect.
2. Fix through the existing owner. Launcher edits must go through RuleCollectionsManager's configuration transaction, merging into the latest state while holding its lease. Never save RuleCollections.json alone or bypass the handwritten-configuration preservation guard.
3. Run the narrow relevant tests. For tour layout, include scene geometry, the production hero layout, and composed-screen snapshots. Do not repeat broad tests without a new reason.
4. Build, sign and install on the Air with `Scripts/air-iterate.sh` (Developer ID signed, not notarized; ~35 s after the build; `--no-build` reinstalls `dist/`). It keeps one rolling backup at `~/.keypath-iterate/KeyPath-previous.app`, preserves rules/preferences and TCC grants, and verifies the owned runtime; a locked Air reports a Secure Input wait instead of failing. It first keeps the Air's display awake for an hour (`agent-awake` from dotfiles, else `caffeinate -d`), because the lock screen holds Secure Input and stops the engine; the Claude app's "keep awake" prevents only system sleep. Do not use `ui-deploy.sh`/`quick-deploy.sh` here: they install on the machine they run on, which is the mini. The older manual description follows for reference: The mini's malpern console session must be logged in for Developer ID signing. Use the Air’s verified companion binaries as the bundle baseline; do not assume the mini’s installed helpers, CLI, or engine match. Compare their hashes before deployment. Verify the signed candidate, transfer it incrementally to a staging bundle on the Air, preserve the previous app, then replace and relaunch. Record the binary SHA-256 and source revision plus dirty-change manifest; a base commit alone does not identify a dirty build.
5. Use **Help → Preview KeyPath Tour…** for visual iteration. Page buttons jump directly to any of four pages; the State picker selects fresh, installed, app-selected, failed-save, existing-setup, or saved-but-inactive fixtures. Changes stay in memory. Closing the preview does not mark onboarding complete. The real Replay Tour remains the integration check for durable saves.
6. Verify the actual installed UI at a fixed window size, all four pages and the affected state. Compare ordinary key bounds, including after selecting an app and navigating backward. Confirm saves in both metadata and generated config, then remove temporary test mappings through the same UI and verify cleanup in both files.
7. Report what changed, tests and live checks completed, exact installed build, and any remaining blocker. Update the checked-issues list with evidence. “Code tested” and “installed and visually verified” are separate states.

Keep restart/recovery work in a separate batch. Use the managed VM lab for clean-install, permissions, reboot, or driver behavior; ordinary tour layout changes do not need a new VM or notarized release. Keep one owner for runtime-changing checks and builds. Use parallel reviewers only when explicitly requested and isolate their edit scopes.
